# 面试讲解与问答

## 1 分钟介绍

我做的是一个企业云产品智能支持与工单协同 Agent。它面向 API 使用咨询和故障报修，先对用户输入脱敏，再判断问题类型和信息是否完整。对于文档内的问题，它会检索知识库并展示引用；对于 429、5xx 等问题，它会调用错误码、额度或服务状态工具。证据不足、出现安全风险或生产环境大面积异常时，系统会创建人工工单，并通过状态机记录后续处理过程。项目使用 FastAPI、SQLite、Streamlit，并支持腾讯混元和离线 Mock 两种模式。我还用固定测试集评估分类、检索、工具选择、升级和脱敏效果。

## 3 分钟介绍

这个项目源于企业技术支持中的一个常见问题：用户通常只会说“接口不能用了”，支持人员需要反复追问错误码、Request ID、发生时间和影响范围，再查询文档、账户与服务状态。如果直接让大模型回答，它容易缺少依据，也无法真正查询业务系统。

因此我把流程拆成四类能力。第一，RAG 只负责从产品文档中提供可引用的依据。第二，Python 工具查询模拟错误码、账户额度和服务状态，保证确定性结果。第三，Agent 根据意图和当前信息选择追问、检索、调用工具或人工升级。第四，工单状态机管理人工处理，记录创建、分派、解决和关闭过程。

在工程上，我先用普通 Python 实现完整流程，再用 LangGraph 包装编排，这样框架不会绑住核心逻辑。大模型通过统一接口接入腾讯混元，没有密钥或网络异常时会降级到 Mock，保证面试现场仍可演示。知识库默认使用离线检索，也支持 Chroma。输入中的 API Key、手机号和邮箱会在写入日志或发送模型前被遮盖。

验证方面，我准备了 42 条固定样例，覆盖知识问答、同义表达、无答案、信息不足、工具调用、人工升级和敏感数据。脚本会计算分类准确率、Recall@3、工具选择、升级判断和脱敏成功率，并保留逐条结果。下一步可以接入真实服务状态、企业工单平台、权限系统和人工审核后的知识回流。

## 12 个常见问题

### 1. 为什么不用大模型直接回答

模型不能可靠查询账户额度、服务状态或工单，也可能编造结论。项目把知识依据交给 RAG，把确定性查询交给工具，把状态流转交给后端代码。

### 2. RAG 和 Agent 的区别

RAG解决“依据从哪里来”；Agent解决“下一步应该追问、检索、调用工具还是转人工”。

### 3. 为什么先写普通 Python 再用 LangGraph

核心业务逻辑需要可测试、可替换。先完成普通工作流更容易定位问题，LangGraph只承担状态编排。

### 4. 如何避免无依据回答

回答只接收检索片段和工具结果。检索分数低且没有工具证据时，系统拒答并创建人工工单。

### 5. 为什么工单状态不用模型决定

状态代表企业流程和审计责任，需要确定性规则。模型可以建议动作，但后端状态机决定是否允许跳转。

### 6. 429 怎么排查

先确认影响范围和账户，再查询错误码说明与模拟额度。处理建议包括降低并发、指数退避和检查 QPS、TPM 与余额。

### 7. 如何处理敏感信息

在数据库、日志和模型调用之前统一脱敏。发现疑似密钥泄露时直接升级人工，并建议吊销密钥。

### 8. 如何评估检索

为每条测试问题标注期望文档，计算正确文档是否进入前三条，也就是 Recall@3，并记录检索失败原因。

### 9. 为什么准备 Mock 模式

真实模型会受网络、额度和账号状态影响。Mock 保证测试可重复，也能让面试现场稳定演示完整业务流程。

### 10. 项目最大的局限是什么

服务状态、额度和工单都是模拟数据，知识库规模也较小。项目验证的是架构和流程，不代表生产可用性。

### 11. 如何接入真实企业系统

把工具实现替换为带鉴权、超时、重试和审计的适配器，保持 Agent 只调用统一工具接口，不直接访问底层系统。

### 12. 如果再做两周会增加什么

加入真实身份权限、外部工单平台、可观测性、人工知识审核、更强的中文 Embedding 和线上 A/B 评测。
